# 0001. Lock-free case store

Status: Accepted (owner decision). No ADR directory or format existed in this repository; this file sets a minimal Status / Context / Decision / Consequences layout.

## Context

The case store serialised writers with an advisory pid lock. Three successive lock designs failed review on the same family of problems: exists-then-create races, an empty-lock window that let a live lock be broken, release deleting a lock it no longer owned, EPERM read as "dead", takeover races, pids that mean nothing across hosts, clock-skew grace periods, races on the break file, old CLIs deleting a new lock format, false EEXIST over NFS, no backoff, init failing while locked, release masking the body's error, and leaked temp files. Each fix added a mechanism that created the next race. The store must also work when several hosts share it.

## Decision

Drop mutual exclusion and use optimistic concurrency built on one primitive, `createExclusive(final, bytes)`: write a temp file in the same directory, `link()` it to the final name, unlink the temp, fsync the directory. `link` fails with EEXIST instead of replacing, so exactly one writer wins and readers never see a partial file. A lost reply (EEXIST with the temp file at two links) counts as a win. Where hard links are unsupported it falls back to an exclusive create of the final name, which is still exclusive but can expose a partial file to a reader. `rename` is never used to claim a name.

- put: write the content-addressed object, claim `<n>.json` for n = newest + 1 (on EEXIST re-list and retry with 1-25 ms jitter, 20 attempts, then a contention error), append the `put` transition, then re-check the object and rewrite it from memory if missing. Revision numbers are never reused.
- trust: one file `keys/<sha256(keyId)>.json`; EEXIST means already trusted. The manifest's `trustedKeys` are a frozen base list; readers use the union.
- init: `mkdir -p`, exclusive manifest create; only the winner records `init`.
- transition log: each writer process appends to its own `transitions.d/<host>-<pid>-<random>.jsonl`, one framed buffer per record in a single write, lines under 4 KB. Readers merge the legacy `transitions.jsonl` and all per-writer logs, skip unparseable lines and collapse identical ones.
- reads: revision files are listed before the log is read; a read without a revision returns the newest vouched one; an unparseable revision with no transition is reported incomplete/unvouched, not corrupt. `getBundle` applies `verifyStore`'s provenance rules to an explicit revision too: a revision no put transition vouches for, or whose bytes no longer hash to the digest the put recorded (the logged digest, never one recomputed from the same bytes), is refused in strict mode and listed in `report.problems` otherwise.
- retention: "newest" is the highest *vouched* revision, taken from the same single listing that produces the report's rows. Unvouched files (a crashed or in-flight put) produce no rows, so they can neither become newest nor be purged.
- purge: record the `purge` line, then unlink the revision. Each object is renamed to `.condemned-*`, revisions and transitions are re-read, and it is renamed back if a surviving revision is vouched by its digest, otherwise deleted.
- leftovers: files named exactly like the store's temp (`.<name>.tmp-<hex>`) and condemned (`.condemned-<digest>-<hex>`) shapes are ignored by readers and reported by `verify`; both start with a dot, which no entry name can, so an entry such as `build.tmp-2` is not a leftover. There is no cleanup command and no time-based logic. A temp that could not be unlinked after a successful `link` is such a leftover; it never turns a won claim into an error.
- log appends: the record is written in a loop until every byte is out (`writeSync` may write partially), failing only when a write makes no progress, and the per-writer log is fsynced afterwards.
- format: the manifest is version 2 (version 1 is still read). Any writer upgrades a version 1 store first, adding the regular file `bundles/.format-v2`, which old CLIs `readdir` as a directory and fail on (ENOTDIR). Fresh stores get it too. Directory listings skip dot-files.
- migration: refused while a version 1 CLI is mid-write. If `<store>/.lock` holds a bare pid whose process is alive (`kill(pid, 0)` succeeds or fails with EPERM), nothing is changed, not even the fence, and the error names the pid and the lock file. A missing, non-numeric or dead-pid lock does not block. Every v1 key is first copied to `keys/` as an exclusive file; the manifest is then re-read and v2 is written only if its bytes equal the ones the keys came from (otherwise start over, 5 attempts, then fail). The pid lock is checked again just before that re-read. After migration the `.lock` file is ignored.
- Testing: all filesystem calls go through an injectable `StoreIO` with `onStep(name)` hooks (`store-io.ts`), so each interleaving is reproduced deterministically.

## Consequences

- No lock to take over, break, leak or mis-release; init and trust never fail because another process is active.
- A reader can see a revision before its transition. `verify` may therefore report an in-flight write as unvouched, and it clears on the next run; no grace period is applied. Reads without a revision never serve an unvouched revision.
- Under heavy contention a put can fail with "too much contention" and must be retried.
- A purge can briefly hide an object; `verify` run in that window reports it missing. Over NFS the purge's re-check can read stale directory attributes, so "an object in use survives" is a local-filesystem guarantee only.
- Log ordering across writers is undefined; consumers look records up by (entry, revision).
- Migration can fail with "kept changing" if an old CLI keeps trusting keys while it runs; retry after it finishes. It can also refuse outright while an old CLI is running.
- A crash can leave temp or condemned files, and a no-link filesystem can leave a partial revision file; `verify` reports both.
- Old (version 1) CLIs are fenced by the manifest version and by `bundles/.format-v2` once a store has been written or initialised by this version; a store that is only read is not touched. What the fence covers and what it does not:
  - Fenced (they fail before writing, because they read the manifest or list `bundles/` first): `put`, `trust`, `verify`, `get`, `list`, and `retention` reports and `--purge`. `trust` and `--purge` may briefly create and remove `<store>/.lock` first; this is harmless.
  - **Not fenced:** `case store retention --record-default-policy`. The old `saveRetentionPolicy` never reads the manifest or lists `bundles/`. It writes `retention.json` (temp file and rename, last writer wins) and appends one line to the legacy `transitions.jsonl`. `case store init` on an existing store also still runs: it creates the directories and an empty `transitions.jsonl` if missing and changes nothing else. None of these touches bundles, objects, keys or the manifest, and new readers handle both results (the policy file is validated on read; the legacy log is merged and tolerates a torn line). They were left unfenced on purpose: making them fail would mean moving the policy file or turning the legacy log into a directory, which changes the on-disk contract for new readers, and the old code would still have written the policy before failing on the log. The consequence is that an old binary can still replace the retention policy of a version 2 store. The policy only changes what a report calls purgeable; a purge still needs the owner to present the token of a report they have read.
  - Not fenced either: an old CLI that took its lock, or read the v1 manifest, before the migration and finishes afterwards. The pid-lock check is made twice around the manifest re-read, so the window is the gap between the last check and the rename, but it is not closed: old `trust` reads the manifest outside its lock and writes it back from that stale copy, so such a write could still put a version 1 manifest back. Keys already copied to `keys/` stay trusted and `bundles/.format-v2` still fences old binaries, and the next lock-free write migrates again, but a key that old command added is only in the manifest it wrote. Do the upgrade when no old CLI is in use.
  - The pid check is only meaningful when the old CLI runs on the same host as the migrating one; a pid says nothing across hosts sharing the store.
